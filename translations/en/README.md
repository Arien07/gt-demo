# gt-demo

In reality, many datasets are unbounded because they arrive gradually over time: users produced data yesterday and today, and they will continue to produce more data tomorrow. As long as your business is still operating, this process never ends, so from any meaningful point of view, a dataset is never "complete"1. Therefore, batch processing programs have to artificially split the data into fixed-duration chunks, for example processing the day's data at the end of each day, or processing the hour's data at the end of each hour. [guide.md](../../docs/guide.md)

The problem with daily batch processing is that changes in the input take a day to be reflected in the output, which is too slow for many impatient users. To reduce latency, you can run the processing more frequently — for example, processing the data of each second at the end of that second — or you can abandon fixed time slices entirely and switch to continuous processing, where each event is processed as soon as it occurs. This is the basic idea of stream processing.

In general, a "stream" refers to data that becomes available gradually over time. This concept appears in many places: Unix's stdin and stdout, lazy lists in programming languages2, file system APIs (for example Java's FileInputStream), TCP connections, audio and video transmitted over the internet, and so on.
