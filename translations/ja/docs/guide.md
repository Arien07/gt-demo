線形性は「直列化可能性」と混同されやすい。二つの名称はどちらも「何らかの順序に並べられる」と言っているように見えるからである。しかし、両者はまったく異なる保証であり、区別しなければならない：

直列化可能性
直列化可能性（serializability）はトランザクションの分離性に関する属性である。各トランザクションは複数のオブジェクト（行、ドキュメント、レコード）を読み書きできる。これは、トランザクションの振る舞いが何らかの直列順序で実行されたのと等価であることを保証する。すなわち、あるトランザクションを完全に実行してから次のトランザクションを完全に実行し、互いに交差しない。この直列順序は、トランザクションが実際に実行された順序とは異なってよい 9。

線形性
線形性はレジスタ（すなわち単一のオブジェクト）の読み書きに対する保証である。操作をトランザクションにまとめることはないため、「書き込みスキューとファントム」のような複数のオブジェクトにまたがる問題を防ぐことはできない。しかし、線形性は新しさに関する保証である。ある操作が別の操作の開始前に終了している場合、後続の操作は少なくとも先行する操作と同じくらい新しい状態を観測しなければならない。直列化可能性にはこの要件はなく、たとえば古い読み取りを許容する 10。

```
upstream upserver_weighted {
    server 192.168.1.10:8080 weight=3;  # 高性能服务器
    server 192.168.1.11:8080 weight=2;  # 中等性能服务器
    server 192.168.1.12:8080 weight=1;  # 普通性能服务器
}

server {
    listen 80;
    server_name ms.com;
    
    location /api/questions/ {
        proxy_pass http://upserver_weighted;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}
```

ロックとリーダー選出
シングルリーダー複製を採用するシステムは、リーダーが実際に一つだけであることを保証しなければならず、複数のリーダーが同時に出現する（スプリットブレイン、split brain）ことを許してはならない。リーダー選出（leader election）の一つの方法はリース（lease）を使用することである。起動する各ノードがリースの取得を試み、成功したノードがリーダーとなる 17。基盤となるメカニズムがどのように実装されているかにかかわらず、線形性を満たさなければならず、二つの異なるノードが同時に同じリースを取得することを決して許してはならない。

Apache ZooKeeper 18、etcd などの調整サービスは、分散リースとリーダー選出を実装するためによく使用される。これらは合意アルゴリズムを利用して、フォールトトレラントな方法で線形性のある操作を提供する（これらのアルゴリズムについては本章の後半で議論する）。リースとリーダー選出を正しく実装するには、「分散ロックとリース」で述べられているフェンシング問題など、多くの微妙な詳細がある。Apache Curator などのライブラリは ZooKeeper の上に高水準な慣用的な解決策をラップし、この作業を軽減できる。しかし、これらすべての調整タスクの基盤は、依然として線形性のあるストレージサービスである。
